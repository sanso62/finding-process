# 잃어버린 프로세스를 찾아서

**Finding Process**

이미 실행 중인 Windows 콘솔 프로세스를 찾아, 작업을 유지한 채
**Windows Terminal 또는 VS Code 통합 터미널로 연결을 옮기는 도구**를 만든다.

## 만드는 이유

VS Code나 터미널 창이 갑자기 꺼져도 그 안에서 실행하던 프로세스는
살아 있는 경우가 있다. 작업은 진행 중인데 화면과 입력 연결을 잃어버린 것이다.
이때 작업을 처음부터 다시 실행하지 않고, 남아 있는 프로세스를 찾아
새 터미널에서 그대로 이어서 사용하고 싶다.

## 원하는 사용 흐름

1. 연결을 잃었지만 살아 있는 콘솔 프로세스를 찾는다.
2. 사용자가 복구할 프로세스를 선택한다.
3. Windows Terminal 또는 VS Code 통합 터미널에 연결해 기존 작업을 계속한다.

## 반드시 지킬 조건

- **실행 상태 유지:** 같은 PID와 메모리, 진행 중인 작업이 유지되어야 한다.
- **사후 복구:** 전용 런처나 데몬으로 미리 실행하지 않은 프로세스도 대상이다.
- **직접 연결:** 목적지 터미널이 입출력을 직접 처리하며, 이관 도우미는 종료할 수 있어야 한다.
- **성공의 기준:** 재시작·대화 이력 재개·화면 복사 중계는 위 목표를 달성한 것으로 보지 않는다.
- **실패 시 보존:** 이관할 수 없는 상태라면 원래 프로세스를 유지하고 이유를 알려준다.

## 새 개발의 출발점

이전 실험에서 인계 API가 성공을 반환해도 실제 출력은 기존 연결에 남았다.
API 반환값만으로 이관 성공을 판단하면 안 된다.

첫 목표는 **별도 시험 프로세스에서 PID·메모리를 유지한 직접 이관을 입증하는 것**이다.
도우미 종료 후에도 출력·입력·창 크기 조절이 동작하는지 확인하고,
이후 프로세스 탐색과 사용자 인터페이스를 만든다.

## 구현 및 시험 실행

C#/.NET 9 기반 시험 도구에서 **이미 실행 중인 별도 시험 프로세스를 Windows
Terminal과 VS Code 통합 터미널로 직접 옮기는 데 성공했다.** 같은 PID·메모리를 유지하고, 모든 이관
도우미가 종료된 뒤 Terminal 입력·화면 출력·창 크기 변경을 로컬 통합 테스트로 확인했다.
이 저장소에는 핵심 소스와 빌드 설정을 포함한다.

현재 지원 범위는 **단일 콘솔 처리 스레드가 주기적으로 쉬는 네이티브 x64 시험
프로세스**다. 일반 프로그램의 복구, VS Code의 끊어진 ConPTY, 여러 콘솔 처리
스레드와 대기 중인 입력의 처리는 아직 검증되지 않았다.

Windows x64와 .NET 9 SDK, 목적지에 따라 Windows Terminal 또는 VS Code가 필요하다.
저장소 루트의 PowerShell에서 실행한다.

```powershell
.\finding-process.cmd           # 목록에서 ↑↓ 선택, Enter로 Windows Terminal에 이관
.\finding-process.cmd --vscode  # 선택한 프로세스를 VS Code 통합 터미널에 이관
.\finding-process.cmd list      # 목록만 출력
```

명령어 바로 아래에 최대 10개 항목을 표시하며, 방향키로 이동하면 나머지 항목도 볼 수 있다.
Ctrl+C로 선택을 종료한다. 현재 로그인 세션의 프로세스를 표시하고, 이관 가능한 항목을 먼저 보여준다.
현재는 신원을 검증한 이 프로젝트의 시험 프로세스만 이관할 수 있으며, `미지원` 항목은 이관하지 않는다.
Enter는 기존 프로세스를 유지한 채 새 터미널에 연결한다. 이관 작업이 이미 시작된 뒤의 Ctrl+C는
프로세스 보호를 위해 해당 작업이 끝날 때까지 종료를 보류한다.

저장소 경로가 사용자 PATH에 등록되어 있으면 다른 폴더에서도 `finding-process`로 호출할 수 있다.
첫 실행과 소스 변경 후에는 자동 빌드하며, 실행 중인 시험 프로세스의 파일을 덮어쓰지 않도록 빌드 결과를
`artifacts/cli/`의 소스별 폴더에 보관한다.

```powershell
dotnet build src/FindingProcess.Lab/FindingProcess.Lab.csproj -c Release
$lab = './src/FindingProcess.Lab/bin/Release/net9.0-windows/FindingProcess.Lab.exe'

# 별도 시험 프로세스의 상태와 기존 콘솔 입출력 확인
& $lab baseline

# 숨겨진 콘솔 사이의 실제 재연결
& $lab rebind-lab

# 연결 실패 시 원래 콘솔로 돌아오는지 확인
& $lab rebind-lab --rollback

# 별도 시험 프로세스를 새 Windows Terminal 창으로 이관
& $lab rebind-lab --terminal

# 별도 시험 프로세스를 새 VS Code 통합 터미널로 이관
& $lab rebind-lab --vscode
```

결과는 `artifacts/`에 실행별로 저장한다. 각 명령은 자체 생성한 시험 프로세스만 대상으로 한다.
실행 파일의 신원을 확인하므로 `dotnet FindingProcess.Lab.dll` 대신 빌드된 `.exe`를 사용한다.

`--terminal`과 `--vscode`는 이관 도우미 종료 후 시험 프로세스를 남겨 수동으로 확인할 수 있게 한다.
출력된 `add 11 <확인 문자열>`을 새 Terminal 창에 입력하고, 누적 값이 18로 바뀌는지와
창 크기 변경이 출력에 반영되는지 확인한다. 이 명령 자체는 Terminal 입출력 검증 완료로
판정하지 않는다. 시험 프로세스는 시작 후 300초가 지나면 종료되며, `quit`를 입력해
먼저 종료할 수도 있다.

VS Code 모드는 `src/FindingProcess.VSCode`의 로컬 확장을 개발 호스트로 로드하여 별도 창을 연다.
설정과 확장 경로는 해당 실행의 `artifacts/` 안에 두며, 기존 VS Code 창이나 사용자 설정은 바꾸지 않는다.
확장은 VS Code의 일반 통합 터미널을 만들 뿐 입출력을 복사하거나 중계하지 않는다.

VS Code에서는 **터미널의 PowerShell 셸이 남아 대상 종료를 기다린다.** 이 셸은 대기 중 입력을 읽지
않으며, 대상이 종료되면 일반 프롬프트로 돌아간다. 이관 작업자·목적지 준비 프로세스·원래 콘솔 보존
프로세스는 모두 종료한다. 셸 유지가 필요한 이유는 VS Code의 터미널 관리가 최초 셸의 수명에
연결되어 있기 때문이다. 별도 상주 셸 없이 동작하는 Windows Terminal 경로와 이 점이 다르다.

기존 데모의 `artifacts/live-*/demo.json`이 있다면 같은 프로세스를 VS Code로 옮길 수도 있다.
아래 경로의 `<실행 ID>`를 실제 폴더 이름으로 바꾼다.

```powershell
& $lab restore-demo './artifacts/live-<실행 ID>/demo.json' --vscode
```

이 명령은 데모의 PID·생성 시각·메모리 표식을 검증하며 데모를 재시작하거나 자동 종료하지 않는다.
실행 중인 데모와 같은 빌드 결과를 덮어쓰지 않도록, 빌드가 필요하면 `dotnet build ... -o <별도 경로>`로
도우미를 따로 빌드한다. 일반 프로그램의 임의 PID 복구는 지원하지 않는다.

자동 종료 없이 현재 콘솔에서 시험 프로세스를 실행하려면 다음 명령을 사용한다.
`add 5`와 Enter로 값을 더하고, `quit`와 Enter로 종료한다.

```powershell
& $lab fixture ./artifacts/manual/fixture.json --forever
```

일반 프로세스의 복구는 아직 구현하지 않았다. 콘솔 호스트를 강제 종료한 로컬 실험에서는
시험 프로세스도 입력 API 오류로 종료되었으므로, 비정상 종료 후 살아남은 프로세스의 복구는
아직 입증하지 못했다.
